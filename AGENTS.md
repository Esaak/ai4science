# AGENTS.md — urban_layer: метрики суррогата LES

Файл-договор с агентом. Агент читает его в начале каждой сессии.

Проект: нейросетевой суррогат LES-расчёта — по застройке, растительности, источнику эмиссии
и ветру модель предсказывает поле концентрации примеси над городским кварталом. Эта папка —
учебная среда курса AI4Science над этим проектом: статья, библиотека, данные-образец и
проверки. Основной код и обучение живут на серверах и сюда не переносятся.

### Сделано: метрики суррогата (неделя 2)

Посчитать метрики качества предсказания по пяти сценам из `data/edison_cache/top_fields.npz`
для двух моделей — `p_combo` и `p_прежняя`.

Должны появиться три файла:

1. **`src/metrics.py`** — модуль с функцией

   ```python
   def metrics(obs, pred) -> dict
   ```

   `obs` и `pred` — массивы numpy одинаковой формы. Функция возвращает словарь ровно с
   ключами `R2`, `FAC2`, `NMSE`, `FB`, `mass_ratio`, значения — числа `float`.
   Определения (Chang J. C., Hanna S. R. «Air quality model performance evaluation»,
   Meteorol. Atmos. Phys. 87, 167–196, 2004; DOI 10.1007/s00703-003-0070-7), по набору пар
   (o, p) из всех ячеек разреза:

   | метрика | определение |
   |---|---|
   | `mass_ratio` | Σp / Σo |
   | `FB` | 2·(ō − p̄) / (ō + p̄) |
   | `NMSE` | mean((o − p)²) / (ō · p̄) |
   | `R2` | 1 − Σ(o − p)² / Σ(o − ō)² |
   | `FAC2` | доля ячеек с 0,5 ≤ p/o ≤ 2 среди ячеек, где o > 0 |

   Все ячейки разреза входят в расчёт, включая нули под зданиями. Исключение одно: `FAC2`
   считается только по ячейкам с o > 0, и знаменатель у него — число таких ячеек.

2. **`results/metrics.json`** — результат в виде

   ```json
   {
     "данные": "data/edison_cache/top_fields.npz",
     "метрики": [
       {"модель": "p_combo", "разрез": "всё", "n": 409600,
        "R2": 0.0, "FAC2": 0.0, "NMSE": 0.0, "FB": 0.0, "mass_ratio": 0.0}
     ]
   }
   ```

   Список `метрики` содержит ровно 16 записей: для каждой из двух моделей — один разрез
   `"всё"`, пять разрезов по слоям (`"слой Z1"`, `"слой Z5"`, `"слой Z8"`, `"слой Z25"`,
   `"слой Mean"`) и два по семействам (`"семейство январские"`, `"семейство urban_layer"`).
   Поле `n` — число ячеек в разрезе. Семейство сцены определяется по полю `campaign` в
   `data/edison_cache/val.npz` по номеру сцены из массива `idx`: префикс `2026_01` —
   январские, остальное — `urban_layer`.

3. **`results/metrics_table.md`** — та же таблица для человека: строки — разрезы, столбцы —
   метрики, отдельные таблицы на каждую модель.

## 1. Критерий готовности

```bash
python3 checks/check.py
```

Код 0 — работа принята, другой код — нет. Проверка пересчитывает метрики своим независимым
кодом и сверяет их с `results/metrics.json`, а также проверяет `src/metrics.py` на случаях
с заранее известным ответом. Запускать её после каждого изменения.

## 2. Карта проекта

- `data/` — образец данных с сервера, закрыт от записи. Описание каналов, слоёв, единиц и
  ловушек — `data/README.md`, прочитать до первого расчёта.
- `paper/` — статья проекта и её разделы; `library/` — 35 работ: запись с аннотацией,
  полный текст в `library/pdf/` и извлечённый текст в `library/text/`;
  `src/` — код; `results/` — результаты; `checks/` — проверки, закрыты от записи;
  `memory/`, `notes/`, `tasks/`, `reports/` — заполняются на следующих неделях курса.

## 3. Инструменты и границы

Можно: читать файлы проекта, писать в `src/` и `results/`, запускать `python3`, вести git
в этой папке. Интерпретатор с numpy — `.venv/bin/python`; системный `python3` numpy может
не иметь.

- Не изменять файлы в `checks/` — `[среда]`: папка закрыта `chmod -R a-w checks`. Критерий

- Не подключаться к серверам `edison` и `neptun`: никаких `ssh`, `scp`, `docker exec` —

  подтверждает человек; в `ai4science run` режим `auto`, и запрет держится только текстом

- Не читать и не выводить `.env` и другие файлы с ключами — `[окно]`.

- Не переносить числа из `paper/paper.pdf` в `results/` — `[окно]`. Статья описывает

## 5. Протокол и режим работы

Режим — ReAct: небольшое изменение, затем запуск. После каждого изменения `src/metrics.py`
или `results/` — `python3 checks/check.py` и чтение её вывода. Проверка упала — исправлять
причину, названную в её сообщении, а не подгонять результат.

Git ведёт агент: коммит в `main` после того, как проверка дала код 0; одна задача — один
коммит; сообщение по-русски, одной строкой, что сделано. `git push` запрещён.

## 6. Память

После каждой задачи — запись в `diary.md` по форме, которая там указана: дата, запрос, что
сделано, результат, точка проверки (команда и её код), итог. Старые записи не менять.

Исключение — прогоны каскада (раздел 0): в них `diary.md` не трогать, запись делается одна
по итогу всего каскада, отдельным прогоном.

## 7. Чего агент не может знать сам

- **`paper/paper.pdf` — срез прежней постановки, а не описание текущего проекта.** Числа
  статьи (R² = 0,86, FAC2 = 0,75, NMSE = 0,44) получены на другой задаче и в `results/` не
  переносятся. Текущее состояние: у модели `combo_family` на `urban_layer_*` R² = 0,813,
  FAC2 = 0,495, NMSE = 2,33 (`urban_layer/docs/state.md`, 2026-10-17).
- В статье четыре высоты и здания 16 м; в проекте слои Z1, Z5, Z8, Z25 — 3, 11, 17, 51 м
  плюс среднее по высоте, здания 14 м.
- В статье нет канала семейства, а сейчас это ключевой элемент модели.
- **`top_fields.npz` — пять сцен с наибольшей ошибкой, отобранных вручную.** Метрики по ним
  характеризуют худший случай, а не модель: отрицательный R² здесь ожидаем и не является
  признаком ошибки в расчёте.
- Нули под зданиями в слоях Z1 и Z5 — это не пропуски, заполнять их нельзя.
- `x[8]` в кэше — константа на сцену, в описании входа модели её нет.
- **Числа из таблиц статьи в `paper/paper.txt` и `paper/sections/` могут стоять не в своих
  столбцах.** Текст извлечён `pdftotext` без `-layout`: в строке Table 2 на с. 10 два
  последних столбца переставлены (верно `NMSE 0.694 → 0.937`, `mass_ratio 0.865 → 0.832`).
  Для чисел из таблиц брать `paper/paper_layout.txt` (проверено 2026-10-19).

## 8. Остановка и бюджет

Окно контекста пересылается целиком при каждом вызове инструмента, а суточный счётчик
берёт из ответа полный `total_tokens`. Поэтому двадцатый шаг стоит почти столько же,
сколько вся история до него, а напечатанное один раз платится заново на каждом следующем
шаге. Замер прогона 2026-10-18 (21 вызов, 588 206 токенов): последние восемь вызовов —
`git add`, `git status`, `git commit`, дописывание `diary.md` — обошлись в 280 тыс.
токенов, 48 % прогона, при 1 304 токенах полезного ответа.

- Не больше 20 шагов (вызовов инструментов) на задачу — `[окно]`.
- Не выводить файл целиком: `wc -l`, `head -20`, `grep -n`, `sed -n '10,40p'`. JSON
  сводить вычислением (`.venv/bin/python -c ...`), а не печатать. Четыре тысячи символов
  `results/metrics.json`, напечатанные на пятом шаге, стоят ещё ~25 тыс. токенов до конца
  прогона — `[окно]`.
- Не читать дважды одно и то же и не проверять то, что уже названо в запросе — `[окно]`.
- Закрывать задачу одной командой, а не восемью:

  ```bash
  .venv/bin/python checks/check.py && git add -A \
    && git commit -m "<что сделано>" && git log --oneline -1
  ```

- Две неудачи проверки подряд с одной и той же причиной — остановиться, не менять больше
  ничего и сообщить: что сделано, что в выводе проверки, какая строка этого файла
  оказалась недостаточной.
- Если для цели не хватает сведений — остановиться и спросить, а не домысливать.
